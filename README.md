# 🗺️ Zivilschutz-Karte (inkl. Offlinekarte) - Fork ZSO Wettingen-Limmattal

## ℹ️ About

Zivilschutz-Karte is a powerful JavaScript application (based on Angular) designed for creating detailed situation maps for disaster management. Developed specifically for Swiss civil defense organisations, it works seamlessly on both standard computers and interactive whiteboards. 🖥️ 📱

## 🔍 Key Features

- 🎨 Intuitive drawing interface
- 🌍 Multiple map provider integration
- 💾 Local storage support
- 🔄 Real-time collaboration
- 📱 Responsive design
- 🔒 Secure authentication

## 🚀 Getting Started

### 🛠️ Prerequisites

- 🐳 Docker 27.x or higher, with the Compose plugin (`docker compose version`). Tested with Docker 29.
- 🐚 A bash shell for `zskarte.sh`: Linux, macOS or WSL2 on Windows.
- 💾 About 3 GB of free disk space (map tiles about 1 GB, search data about 200 MB).
- 🌐 Free ports on this machine: 1337, 4300, 7050, 8000, 8080, 55432.
- Only for development outside Docker: Node.js 22.x and npm 10.x (the Docker images use Node 22.22).

### 📋 Installation Steps

### 1. Download the map and search data (once, repeat e.g. twice a year)

```bash
./zskarte.sh init
```

### 2. Start all services

```bash
./zskarte.sh start      # add -b to force an image rebuild
```

On the first start the `.env` files are created from the `.example` files. The example values work for local development; change them before you use the system anywhere else.

### 3. Access the Strapi admin panel (Backend)

1. http://localhost:1337/admin
2. Login with credentials: User -> info@zskarte.ch, Password -> Supersecret123

### 4. Access the Zivilschutz-Karte application (Frontend)

Zivilschutz-Karte is optimized and tested for use with Google Chrome - nevertheless other browsers might work as well and are supported in a best effort manner.

1. http://localhost:4300
2. Login with credentials: User -> zso_development, Password -> Supersecret123

## 🛠️ Development Tools

### 🐳 Docker-Compose

This starts the PostgreSQL database for the backend (Strapi), the search database and pgAdmin.

#### First setup (downloads data, about 1 GB)

```bash
./zskarte.sh init
```

#### Start

```bash
./zskarte.sh start        # add -b to force an image rebuild
```

#### Stop

```bash
docker compose -f zskarte/docker-compose.yml down
docker compose down
```

Data is kept in the Docker volumes `zskarte_pgdata-zskarte` and `zskarte_pgadmin-zskarte`. `down` keeps them; `docker compose down -v` deletes them.

### Configuration (deploy.env)

All hostnames and the Traefik settings are set in one file: `deploy.env` (copy of `deploy.env.example`, not in Git). `zskarte.sh` creates it on the first run and reads it for every command.

| Variable | Meaning |
|---|---|
| `ZSK_TRAEFIK` | `false`: local, services on `localhost` ports. `true`: behind Traefik, services on the hostnames below |
| `ZSK_TRAEFIK_NETWORK` | Docker network of Traefik (e.g. `proxy-network`) |
| `ZSK_TRAEFIK_ENTRYPOINT` | Traefik entrypoint for HTTPS (e.g. `websecure`) |
| `ZSK_TRAEFIK_CERTRESOLVER` | Traefik certificate resolver (e.g. `myresolver`) |
| `ZSK_APP_HOST` | Frontend, e.g. `maps.example.org` |
| `ZSK_API_HOST` | Backend API (Strapi), e.g. `api.maps.example.org` |
| `ZSK_SEARCH_HOST` | Address search API |
| `ZSK_TILES_HOST` | Map tile server |

With `ZSK_TRAEFIK=true` `zskarte.sh` also:
- adds `zskarte/docker-compose.traefik.yml` and `docker-compose.traefik.yml`. They connect the four services to the Traefik network, create the routers for the hostnames above and remove the direct host ports (only Postgres and pgAdmin stay, bound to `127.0.0.1`).
- writes the public URLs into the frontend at build time (`https://<host>`, search under `/search/`, tiles under `/styles/osm-bright`).

**Changing a hostname or the Traefik mode:** edit `deploy.env`, then run

```bash
./zskarte.sh start -b
```

`-b` is required, because the frontend URLs are compiled into the app image. A change only in the Traefik labels also needs `-b` in practice, since the app image and the labels are applied together.

Frontend URLs are generated by `zskarte/packages/app/scripts/write-environment.js` during the image build (from the build arguments `ZSK_API_URL`, `ZSK_SEARCH_URL`, `ZSK_TILE_URL`). Do not edit `environment.prod.ts` by hand; change `deploy.env` instead.

### Database access

Postgres and pgAdmin are only reachable from the local machine (`127.0.0.1`).

- PostgreSQL (backend): host `localhost`, port `55432`, user `postgres`, password `supersecret123`, database `zskarte`
- pgAdmin: [http://localhost:7050](http://localhost:7050), login `info@zskarte.ch` / `zskarte`
- pgAdmin already has the server "postgres-local" configured (`zskarte/packages/server/init/servers.json`)

> ⚠️ These are example passwords. Change them before you use the system anywhere else.

#### Changing the database and pgAdmin passwords

The passwords are not set in `deploy.env`. They are written in several files, and all of them must match:

- `zskarte/docker-compose.yml`: `POSTGRES_PASSWORD` and `DATABASE_PASSWORD` (server), `PGADMIN_DEFAULT_EMAIL` and `PGADMIN_DEFAULT_PASSWORD` (pgAdmin)
- `zskarte/packages/server/config/database.ts`: fallback value of the database password
- `zskarte/packages/server/init/servers.json`: the password pgAdmin uses for the "postgres-local" connection
- `searchserv/search-db.env` and `searchserv/search.env`: password of the search database (separate from the main database)

Postgres and pgAdmin read their initial values only when their data volume is empty. On an existing installation:

1. Change the password inside the database: `docker exec -it postgresql-zskarte psql -U postgres -c "ALTER USER postgres PASSWORD 'new-password';"`
2. Change the same password in the files above and restart with `./zskarte.sh restart -b`.
3. For the pgAdmin login, change the password in the pgAdmin web UI (user menu at the top right, "Change Password"), or delete the `pgadmin-zskarte` volume to start over (this removes pgAdmin's saved settings).

To check the versions of the running containers:

```bash
# image names of the running containers
docker ps --format "{{.Names}}  {{.Image}}"

# PostgreSQL version of the backend database
docker exec postgresql-zskarte psql -U postgres -tAc "select version();"

# PostgreSQL and PostGIS version of the search database
docker exec offlinekarte-search-db psql -U postgres -tAc "select version();"
docker exec offlinekarte-search-db psql -U postgres -tAc "select postgis_full_version();"
```

### DB Migration (from the old installation with PostgreSQL 16)

The old setup (commit `6947bc4`) ran PostgreSQL 16.3 with a bind mount in `zskarte/data/postgresql`. PostgreSQL 18 cannot read that data directory, so the data is moved with a dump and restore. Make the backup first and keep it until the new installation is verified.

1. **Backup** (old installation still running):

   ```bash
   # dump inside the container (binary output is corrupted by shell redirection, e.g. in PowerShell)
   docker exec -e PGPASSWORD=supersecret123 postgresql-zskarte pg_dump -U postgres -w -Fc -f /tmp/zskarte-pg16.dump zskarte
   docker cp postgresql-zskarte:/tmp/zskarte-pg16.dump ./zskarte-pg16.dump
   ```

   Also copy `zskarte/packages/server/public/uploads` if it exists (not in Git).

2. **Stop the old installation**, keep its `data/` folder as fallback.

3. **Start the new version** (empty database, example data from `init.sql`):

   ```bash
   ./zskarte.sh init
   ./zskarte.sh start -b
   ```

4. **Restore the backup into an empty database.** A restore with `--clean` into the database that already holds the example schema fails on foreign keys (`cannot drop constraint ... because other objects depend on it`). Recreate the database first, then restore:

   ```bash
   # stop the backend so nothing reads the tables
   docker stop server-zskarte

   # empty database (FORCE closes open connections, e.g. from pgAdmin)
   docker exec -e PGPASSWORD=supersecret123 postgresql-zskarte psql -U postgres -w      -c "DROP DATABASE IF EXISTS zskarte WITH (FORCE);"      -c "CREATE DATABASE zskarte;"

   # restore into the empty database (no --clean needed)
   docker cp ./zskarte-pg16.dump postgresql-zskarte:/tmp/zskarte-pg16.dump
   docker exec -e PGPASSWORD=supersecret123 postgresql-zskarte pg_restore -U postgres -w -d zskarte /tmp/zskarte-pg16.dump

   # start the backend again; Strapi applies its schema migrations (5.33 to 5.63) on this start
   docker start server-zskarte
   docker logs -f --tail 30 server-zskarte
   ```

   Wait for `Strapi started successfully`. The dump from step 1 remains the only fallback, the migrations cannot be reverted easily.

5. **Check:** log in to the Strapi admin, count the journal entries, open a map with signs.

> ⚠️ The step above drops and recreates database `zskarte`. Everything in it is replaced by the backup, so do not store anything else there.
